Connect your backend to CellPilot

Your backend drives the cellular module and keeps the messages and call history. The CellPilot app does everything on the phone. When the phone has to be woken, the push goes through the CellPilot relay to Apple, sealed so the relay cannot read its contents. Start with Getting started, then look up each API by group.

Getting started

Read this group first: what you do and what CellPilot does, the order to build in, and the conventions every API shares. This page is derived from the specification, spec/device-api.md in this repository, and adds no rules of its own; where the two disagree, the specification wins. A note marked “reference backend” describes what the reference backend does within the rules, not something you must copy.

Who does what

The app knows only the Device API. It does not care what hardware your backend drives, what language it is written in, or where it runs. Any backend that implements the API works with the app.

Lawful use. CellPilot is made only for lawful purposes. We abide by the law and do not endorse, support or assist any unlawful activity. If you find a problem — misuse, or anything in the product or these documents that conflicts with laws or regulations — please tell us right away at abuse@cellpilot.dev. We will cooperate with the authorities and rectify it, and if necessary change, restrict or shut down the feature or service concerned. CellPilot is meant for one person using their own SIM from their own devices; it is not a replacement for phone service and must not be relied on for emergency calls (an emergency call leaves from the module's location and may reach the wrong emergency centre).

You do

  • Drive your module or SIM: send and receive messages, make and take calls, read the signal.
  • Implement the core of the Device API, then declare the optional features you can deliver.
  • Keep the data: messages and call history, and optionally contacts and voicemails.
  • Decide how the app reaches you: LAN, VPN or tunnel, any of them.

CellPilot provides

  • The iOS app: the interface, CallKit for incoming calls, call audio, notifications.
  • This specification, the conformance checker api-check, the relay stand-in test-relay and the smallest backend mock-backend.
  • The push relay push.cellpilot.dev: it takes the pushes you seal and delivers them to the phone. You need no Apple developer account.

Implementation path

Build in this order; each step can be checked on its own. Steps 2 and 3 are the minimum: with them the app can send and receive messages and make calls through your backend.

  1. (Optional) Look at a working minimal backend first. tools/mock-backend.mjs in this repository implements only the core, in one file with no dependencies; messages and calls are simulated. Run it and connect to it from the app's pairing screen with “Enter address”. Skip this step if you like.
  2. Implement the core. Discovery, pairing, the client record, status, the call, the history, messages, the event stream. The core checklist lets you tick them off.
  3. Check it. Use tools/api-check.mjs. By default it only reads: it never dials or sends a message, and it is designed not to change anything, so it can be run against a backend with a real SIM. It checks every response and event frame field by field against openapi.json and events.schema.json. A backend with a simulated device can add the write and simulation-hook checks; see Testing tools.
  4. Declare the optional features you have. Declare each one when it works. For an undeclared feature the app shows no button and sends no request.
  5. Add push. Pushes go through the CellPilot relay, and the app does the enrolment for you; see the Push group.
Terminal
# 1. Start the minimal backend; the console prints a six-digit pairing code
node tools/mock-backend.mjs --port 8799

# 3. Check your own backend (the token comes from a pairing)
node tools/api-check.mjs --url http://192.168.1.10:9400 --token <a paired client's token>

Conventions

Every API is under /v1, and these conventions hold for all of them.

TopicConvention
FormatJSON in both directions, keys in camelCase. Your responses carry Content-Type: application/json; charset=utf-8. A request body is read as JSON whatever its Content-Type, so you need not check it: no body is {}; a body that is not JSON, or JSON that is not an object (an array, a string, null), is 400 invalid_request (without details); unknown fields are ignored. You may refuse a body larger than a size you choose with 413 invalid_request (reference backend: 8 MB). Every successful response is a JSON object: a collection sits under a named key ({ "messages": [...] }), a single resource is the object itself, and a deletion returns {}.
FieldsEvery field listed for an object is always present. One that is unknown, does not apply, or belongs to a feature you do not declare (place without places, name and contactId without contacts) is null, not left out; an empty list is []. Only the fields in the “Optional fields” table below and those marked optional may be left out.
RoutesAn unknown path, and a known path asked with a method it does not take, are both 404 not_found (after authentication). There is no 405.
Times and durationsISO 8601 in UTC, in fields whose names end in At: "2026-09-25T08:14:03.120Z". Durations carry their unit: durationS.
IdsThe id of a message, a call record and so on is a positive integer, a newer record having a larger one. An id in the path that is not a non-negative integer is 400 invalid_request with details.field "id".
AuthenticationEvery request except GET /v1, GET /v1/ping and POST /v1/pair (marked “No auth” by the API name) carries the token: Authorization: Bearer <token>, or X-CellPilot-Token: <token> when the endpoint sets tokenHeader. Accept both (when both are sent, read X-CellPilot-Token; the other one is the proxy's). Store only a hash of the token.
• No token, or a token you never issued: 401 unauthorized.
• A token you revoked, or one whose client unpaired itself: 410 signed_out. To recognise it, keep its hash after revoking.
• After a pairing with the same uid, the old token is simply unknown: 401.
The app treats a 401 or 410 on a token that worked before the same way: it forgets the token and everything it cached and shows the pairing screen.
Paging?beforeId=<id>&limit=<n>: items are ordered by id, largest (newest) first, and only those with an id below beforeId are returned. limit defaults to 100 and is clamped to 1–500 rather than refused. A beforeId or limit that is not a number is ignored. A page shorter than limit is the last one. This is the general rule; a route that names its own default and cap (search 50 / 200, log 200 / 1000) uses those.
LanguageEvery human-readable string you produce (an error message, a failure reason, a place, an alert, a log line) is in the reader's language. There are only en and zh: a value starting with zh (such as zh-Hans) is zh, anything else is en. Numbers, what the user typed, and names are never translated.
• HTTP requests: use the X-Lang header (the app sends it on every request); without it, the lang on the client's record (given at pairing or with PATCH /v1/client); without either, en.
• Event stream: each socket uses the lang on the record of the client it belongs to. Clients with different languages get the same event worded each in its own language.
• Records several clients read (a message's error, a call record's endReason): keep the cause, and word it for each reader when it is read. Do not store a translated sentence.

Numbers and conversations

A number with a country code is read by that country's rules; one without, by the rules of the SIM's home country or region (ISO 3166-1 alpha-2); what neither reads is shown as one run of digits.

Three rules: a number is stored as it came; the same number is filed under the same peer; a number is read only to show its place, and never rewritten.

Stored as it came, less its grouping

  • A number the user typed or the network delivered keeps its digits, a leading +, and the * and # of a USSD code. Spaces, dashes, dots and brackets go.
  • Nothing is added: no country code, no area code. The device's own number (read from the SIM or typed by the user) is no exception.
  • A value with no digit at all (anonymous, a withheld caller) is no number and is stored as "". An SMS sender is the exception: it can be a name (EXAMPLECO). It is kept as it came (trimmed), is a conversation of its own, matched exactly as a string, and never joined to any number.
  • Message.peer, Conversation.peer, CallRecord.peer, Voicemail.peer, Call.number, a contact's numbers and ownNumber are all stored forms.
  • The number of POST /v1/call/dial and the to of POST /v1/messages are stripped of grouping before their checks, and go to the module as typed.

One person, one conversation

When you record a new message or call, first look for a peer already on file (in the messages or the calls) that is the same number by the matching rule of the contact list (digits only; equal, or one the tail of the other with at least 7 digits). Use that exact peer if it is there; otherwise the most recently active match; only when there is none, the number itself. So +8613800138000 from the network and 13800138000 as typed end up in one conversation. Conversations are grouped by the peer string, a {peer} in a path is matched exactly as a string, and the app sends back the peer you gave it.

Read only for the place

Reading a number only says what kind it is and what the full number is, to look up its place (place, carrier, with places). The stored number never changes because of it.

The rules follow how networks and people write numbers. A call from abroad, and every call while the SIM roams, arrives with + or 00 and its country code (3GPP TS 23.081 §1.2.1). Only callers from the SIM's own country arrive in national form, and only landlines of the SIM's own area arrive without their area code. A user knows where the SIM is from and writes numbers the same way. So a country code or area code that is not in the number is never assumed, except for that one local-landline case. Corrupted caller ids and typos are not catered for.

Where the device is, and the phone's own region, play no part. International and service numbers have a place (a hotline's from its own country); gateway and unresolved numbers have none rather than a guess. What a country issues, and how its numbers are grouped, come from libphonenumber's tables (+1 numbers belong to the territory that issues them, such as Canada, and are grouped the way the United States writes them). The full table of cases (what is stored, what it reads as, how it is shown, its place) is fixtures/number-rules.json in this repository; you can test your implementation against it.

How the app shows numbers. It only groups the stored digits the way the number's country writes them. National stays national (an area code typed without its zero is shown without it: 571 2345 6789), + stays international, and 00 with a country code is shown with + (0085261234567 → +852 6123 4567; stored and dialled as it came). A trunk zero after a country code is not shown (+61 412 345 678). A local landline is grouped as the whole number would be, but shown without the area code (23456789 → 2345 6789). Short codes, gateway senders and unresolved numbers are one run of digits. So you need not, and should not, “complete” a number for the user.

Compatibility

We intend version 1 of the API only to grow; it is designed so that an app update does not break a backend that works. That means:

  • Nothing documented is removed or changes meaning, and no field changes type.
  • New things arrive only as new optional fields, new event types, or new features a backend declares. For anything you have not implemented, the app has a fallback.
  • Both sides ignore fields, events and features they do not know; neither may fail on something new.
  • Error codes are stable; an unknown code is treated by its HTTP status.
  • A change that cannot keep these promises would be version 2, with its own /v2, and the app would keep speaking v1 to you.

We may still change or withdraw something when security, law, Apple's platform rules or the relay's operation require it; such changes are announced in CHANGELOG.md. Nothing here is a warranty of continued compatibility or availability.

If your “code” is already a long secret, you may return it as the token.
  • Rate limiting. Failures are counted by source address, so a code cannot be guessed by trying. What the reference backend does (the counts and times are recommendations):
    • What counts as a failure: a wrong pairing code, and a token you do not know (each distinct value once, so the same value sent again adds nothing). A request with no credential at all, and a revoked token (answered 410), do not count.
    • Five failures from one address in 10 minutes block it for 15 minutes. Any successful authentication from the address (any client's valid token) clears its count.
    • While blocked, only another guess is refused: an unknown token, a wrong pairing code, or a wrong portal code is answered 429, without counting. A token that works and the right pairing code are answered as ever; a revoked token is still 410.
    • Every 429 carries Retry-After (the event stream's upgrade refusal included): the seconds the block has left.
    The block is by source address, but it never stops a valid token, so phones behind the same proxy or tunnel are not locked out together.
  • The same uid pairing again: keep the client id, issue a new token, and from then on answer 401 to the old token (it is no longer one you know). Close the event-stream sockets opened with the old token. uid is a 36-character UUID string; anything else is ignored, and the pairing is treated as a new phone.
  • code missing or not a string is 400 (details.field: "code"). This is not a failed attempt and spends no code.
  • name is trimmed and cut to 60 characters; empty or not a string, it is "iPhone". lang is zh when it is a string starting with zh, otherwise en.
  • What goes in endpoints. After pairing the app reaches you only through this list (it falls back to the address it paired with only when the list is empty), so it must hold at least one path the phone can reach. Give addresses that stay right: on the LAN a Bonjour name (http://my-mac.local:9400), not a DHCP address that changes. label is shown in the app's settings, in this client's lang (reference backend: Local network for en, 本地网络 for zh). Every time you return the endpoint list (here, GET /v1/client, the client event), word it in the reader's language.
  • Store only a hash of the token. A lost token means pairing again.
  • You may accept pairing on some addresses only: the reference backend accepts POST /v1/pair on the local network only, so it does not accept pairing from the Internet.
  • To let the app find you, publish _cellpilot._tcp over Bonjour on the LAN (TXT records api=1, path=/). You can skip it: the user can type the address instead.

Endpoints and remote access

An endpoint is one path: an address, plus what it takes to get through the proxy or tunnel on that path. You can give several. The app connects through the best endpoint that answers, by priority: endpoints better than the one in use keep trying to open the event stream, and the app moves up as soon as one gets through; worse ones are left closed until the path in use fails. When the list changes, send a client event, and the app reconnects as needed.

FieldWhat it does
id · labelRequiredAn identifier, and a name shown in the app's settings.
urlRequiredThe base URL, without /v1 (the app appends /v1/…).
priorityRequiredLower is preferred. The app uses the most preferred one that connects, and moves back when a better one recovers.
headersOptionalAdded to every request and to the event stream through this path: a tunnel's service token, a proxy's credentials.
tokenHeaderOptional"X-CellPilot-Token" when a proxy takes Authorization for itself; the app then sends its token in this header.
tlsPinOptionalSHA-256 of the server's certificate (DER), base64 (hex, with or without colons, is read too). The app trusts that certificate for this endpoint whoever issued it, and refuses any other. For a self-signed certificate.
clientCertificateOptionalThe certificate the app presents when the server asks for one (mutual TLS): { "p12": "<base64>", "password": "…" }.
vpnOptionalThe VPN the phone has to be on to reach this endpoint, such as "Tailscale". When the endpoint does not answer, the app asks the user to turn it on. “VPN” here means a private network back to your own home network, not a service for reaching sites blocked where you are; follow the laws on network access where you live.

Whatever the path, two things must get through

  • WebSocket. The event stream stays open so the app gets messages and calls live. A proxy must pass the upgrade (the Upgrade and Connection headers) and allow idle connections of at least 30 seconds; your backend pings every 10.
  • The token. In Authorization: Bearer by default, or in X-CellPilot-Token when the endpoint has tokenHeader.

Computing the fingerprint and building the client bundle

Terminal
# tlsPin: SHA-256 of the server certificate's DER, base64
openssl x509 -in server.crt -outform der | openssl dgst -sha256 -binary | base64

# clientCertificate.p12: the client certificate and key as a password-protected PKCS#12, then base64
openssl pkcs12 -export -inkey client.key -in client.crt -out client.p12 -passout pass:your-password
base64 -i client.p12

When the certificate changes, tlsPin changes with it. That is a change of the endpoint list, so send a client event as usual.

The pairing address. Pairing uses the address the user typed. An endpoint's headers, tlsPin and clientCertificate arrive only in the pairing response, so the pairing address must work without them. The reference backend accepts pairing on the local network only, so it does not accept pairing from the Internet; after pairing the app uses only the endpoint list.

How call records are written

Each call has one record, which you write at three moments of the call. Call.id is this record's id.

WhenWhat you write
It starts: an incoming call rings, or the module takes a dialA new record: outcome: "in-progress", startedAt now, answeredAt, endedAt, durationS null.

It endsendedAt; for a call that connected, durationS (seconds from connecting to the end, rounded to whole seconds; for a call the machine took, from its pickup, also after a take-over, whose answeredAt stays the machine's pickup); the final outcome from the table below.   • No calls event goes out when a record is made or connects; meanwhile the app follows the call through call events. calls goes out when a record ends, is seen or deleted, or a contact's name changes (and when a client takes a call over from the answering machine, the record becoming answered).

Voicemail and transcription

Features voicemail and transcription: your answering machine takes calls for the user.

How the answering machine works

With the voicemail feature, your answering machine can pick up calls for the user and record messages. This section follows a call the machine takes from start to end.

StageWhat you doWhat the app sees
PickupTwo cases: an incoming call rang settings.voicemail.answerAfterS seconds unanswered (reason: "no-answer"; not when the machine is switched off); or the user declined and the app called POST /v1/call/screen (reason: "declined"). You pick up only with call audio flowing; when the audio path fails to start, hang up instead, and the call is a missed one. You pick up and write outcome: "voicemail" on the record.A call event: state: "active", holder: null (no client is on the call).
Recording startsSend a voicemail event: recording: true, transcript: "".The app shows that the answering machine is taking the call.
RecordingWith transcription, send a voicemail event for each recognised piece: transcript is the whole text so far, delta the new part. Without transcription, send none.What the caller says, live.
EndThe caller hangs up, maxSeconds is reached (you hang up), or the user takes the call over (below). Send a voicemail event: recording: false, transcript the final whole text ("" in the event without transcription, never null; the saved voicemail's transcript is null when nothing was transcribed). When the call ends while the machine records (the caller hangs up or the limit is reached), send call (null) and calls first, then this voicemail event, then voicemails. Call audio failing while the machine records ends the recording there: keep what came before and hang up. A recording that holds a message (sound above the line's own noise, or, where it was transcribed, words) is kept as a voicemail: send a voicemails event and a voicemail push. Anything else (under a second, or silence however long) is no message: keep nothing of it, end the call record as missed (outcome: "missed", answeredAt and durationS null, seen: false), and send a missed-call push (“Missed call · no message left”).The voicemail appears in the list.
voicemail events
{ "type": "voicemail", "recording": true, "peer": "+8613812345678", "reason": "no-answer", "transcript": "" }
{ "type": "voicemail", "recording": true, "peer": "+8613812345678", "reason": "no-answer", "transcript": "Hi, this is the building manager", "delta": "this is the building manager" }
{ "type": "voicemail", "recording": false, "peer": "+8613812345678", "reason": "no-answer", "transcript": "Hi, this is the building manager. The water will be off tomorrow." }
  • Taking the call over: while the machine has the call, a client calls POST /v1/call/claim or POST /v1/call/answer. You stop recording, the line stays up, this client becomes the holder, and its audio is connected. The events are call (the new holder), calls (the record now answered), and only then the machine's voicemail (recording: false). When the call ends the record is completed (with a calls event), answeredAt still the machine's pickup and durationS counted from then. What was recorded is still kept as a voicemail if it holds a message, but no voicemail or missed-call push is sent: the user is on the call.
  • peer is the caller's number (stored form), "" when withheld.
  • The answering machine's switch only decides whether it picks up; the voicemail feature stays declared with the switch off; see Features.
  • Recording and consent: recording a caller, transcribing the recording and letting the user follow it live may, depending on where the caller and the user are, require telling the caller or getting their consent. A backend should play a greeting saying that the call is answered by a machine and recorded. Complying with local law is the responsibility of whoever runs the backend. Recordings and transcripts stay on the backend.

Audio frames

Call audio travels as binary frames on the event stream's WebSocket, in both directions, only between the holder and you. Each frame is 323 bytes: a 3-byte header and 20 ms of sound.

OffsetLengthContent
01Direction: 0x01 downlink (you → app), 0x02 uplink (app → you)
11Sequence number, high 8 bits
21Sequence number, low 8 bits (the sequence number is a 16-bit big-endian integer)
3320PCM: 16-bit signed little-endian, 8 kHz, mono; 160 samples = 20 ms
One frame (hex)
01 00 2A  F4 FF 02 00 1C 00 … (320 bytes of PCM in all)
│  └──┴── seq 0x002A = 42
└──────── 0x01: downlink
  • Sequence number: 16 bits, one more for each frame sent, wrapping from 65535 to 0; each direction keeps its own. The receiver compares with serial arithmetic: d = (seq − last) mod 65536, last being the sequence number of the newest frame it played. d == 0 is a duplicate and d > 32768 a frame older than last; both are dropped. 1 ≤ d ≤ 32768 is a new frame: play it and set last = seq.
  • Only with the holder: downlink goes only to the holder's sockets (when a client is connected through several endpoints, each socket gets the same frame with the same sequence number, and the app plays it once); uplink is accepted only from the holder, and anything else is dropped.
  • Pacing: downlink is sent as the audio comes, one frame every 20 ms, not in bursts; the app sends uplink as it captures it, one frame every 20 ms. There is no codec: raw PCM.
  • Silent uplink frames do not claim anything; when one client has several sockets, you may use the signal level to decide which one is live.
  • When it starts: see the audio event under Event stream. A backend with no audio path sends no audio frames, and status.audio.ready is false.

Push

Feature push: when the app is not in the foreground, only Apple's push can wake it. You seal the push and hand it to the CellPilot relay, which passes it on to Apple. This group covers the routes you implement and the format of the pushes; the relay's routes are in the next group.

Push from start to finish

What push needs is spread over several places; this section ties it together. First a one-time setup; after that, every happening goes “ask the live app first, then decide whether to push”.

Setup (once per client)

  1. The app registers its push tokens: POST /v1/client/push-tokens (alert for ordinary notifications, voip for calls).
  2. The app reads GET /v1/push; on mode: "none" it gets a one-time grant from the relay and hands it to you: POST /v1/push/enrol.
  3. With the grant you enrol your public key on the relay: POST /v1/daemons, and keep the daemonId. From then on you sign every push with your private key; see Signing relay requests.

A call comes in

  1. It starts ringing. Make the call record (in-progress) and send a call event to every socket (state: "incoming", holder: null).
  2. Once the number is known (or after 2 seconds of ringing without one, as a withheld number), tell every client: to those with a VoIP token, send the VoIP call push at once, and remember whom you sent it to. Those without a VoIP token are asked first (notify, kind: "call", wait 1.5 seconds): on foreground, no push; otherwise a call alert.
  3. The ringing stops (a client answered, a client declined, the caller gave up, the answering machine picked up): take the system call screen down on the clients that got a VoIP call push; the rule is in When the ringing stops.
  4. The call ends. Write the final outcome and send call (null) and calls events (for a call that ended while the machine recorded, the voicemail event with recording: false comes after these). If it is missed: send a badge event, then ask every client with notify (kind: "missed", wait 5 seconds), and push a missed-call alert to those that did not answer foreground.
  5. The answering machine finishes. Send a voicemails event, then notify the same way with kind: "voicemail" and push a voicemail alert (a recording that holds no message makes no voicemail; push a missed-call instead, its body “Missed call · no message left”).

A message comes in

  1. Record it and send message and conversations events. For a long message, send message for each part, and go on to the steps below only once it is complete.
  2. Send a badge event, then ask every client with notify (kind: "sms", id: "sms-<id>", wait 5 seconds). No push to those answering foreground; the others get an sms alert carrying the current badge.
  3. Later the user reads it on phone A: a conversations event. The badge moved, so send a badge event to the connected clients and a badge-only push to those not connected (changes within 300 ms are sent once, events and pushes alike).

Without the notify feature, skip the asking and push straight away. The full table of what each happening sends is What each happening sends. The details are in: notify and ack (the exchange), Push payloads (what each push looks like), Push encryption, Push routing (whom to push and how to save quota), Push through the relay and The relay's answers.

Push encryption

Push contents are sealed with a key that differs for every client, so neither the relay nor Apple can read them. The key is derived from the client token, which both sides already have, so nothing extra is exchanged.

Key
key = HKDF-SHA256(ikm = SHA-256(token), salt = "cellpilot", info = "push-v1", length = 32)
  • token is this client's token (UTF-8); ikm is the 32 raw bytes of SHA-256. You already store the token's SHA-256 hash (hex); its bytes are ikm.
  • The content to seal is a JSON object (the fields of each push are in Push payloads), encoded as UTF-8 and encrypted with AES-256-GCM: a fresh random 12-byte nonce each time, no additional data (AAD), a 16-byte tag.
  • Join nonce ‖ ciphertext ‖ tag, encode it as base64url (-, _, no =), and put it in the push's e field, alongside "v": 1.
  • Seal for each client separately: the same happening pushed to two clients is two different e.

When the ringing stops

This is the one place it is written out in full; the other places link here.

  • When: the moment the call leaves incoming (it connects, or it ends).
  • reason: connected, and a client answered it → answered; connected, but your answering machine took it (the user's screen included) → unanswered; ended without connecting, within 15 seconds of a client's POST /v1/call/hangup → declined; anything else (the caller gave up, nobody answered) → unanswered.
  • To whom: every client that was sent a VoIP call push for this call, except the one that answered, the one that declined (its hangup within the 15 seconds), and the one that sent it to the machine (its screen within the same 15 seconds). Those already know the ringing stopped. A client never sent a VoIP call push is not among them.
  • How: first send it a notify (kind: "call-end", id: "call-<callId>", with callId and reason) and wait 1.5 seconds. An ack (foreground or background) means it took its call screen down itself: no push. No answer, or no live socket: send the VoIP end push above.
  • Acknowledged ahead: a client whose system never showed the call (Focus held it back) may send its ack (kind: "call-end", id: "call-<callId>") before you ask. Note it; when the ringing stops, neither ask it nor push it. An end push would have to be reported as a call again, and, when Repeated Calls is on (the default), Focus lets a second call from the same number through, so the phone would flash a call screen.

Badge only

A badge-only push
{ "aps": { "badge": 3 } }
  • The only push that is not sealed. Its type is alert, it has the single key aps.badge, and no collapseId.
  • The badge (the same for every client): unread incoming messages not in the trash + call records with seen false + voicemails with heard false + unacknowledged alerts. A feature you do not have counts 0. The same number goes in hello and the badge event, the snapshot's badge, and an alert's aps.badge.
  • Changes within 300 ms are sent once (the badge event too), and only when the count differs from the one last sent. There is one “last sent” for the whole backend, set by any push or badge event to any client, starting from the count when the backend started.

Push routing

Every push the relay actually sends on to Apple counts against the user's hourly and daily quota: alerts, VoIP pushes and badge-only pushes alike; one the relay refuses costs nothing. A push to a client that has already shown the thing spends the user's quota for nothing. Limits, quotas and how they are counted are set by the relay and may change; values in examples are illustrative.

Decide for each client on its own

  1. Does it have a live event-stream socket? No: push straight away. “Live” means the WebSocket answers pings in time.
  2. It has one: ask first. Send notify and wait for the ack. On foreground, no push; on background, or no answer within the wait (1.5 seconds for a call, 5 for the rest), push. Needs the notify feature.
  3. Push to this client only. Use only the tokens this client registered; do not push to all the user's phones at once.

The question goes to every paired client that has a live socket now, whether or not it registered a push token. When a client without a token answers background or does not answer, there is nothing to push, and nothing is done.

The text to sign
METHOD + "\n" + PATH + "\n" + TS + "\n" + NONCE + "\n" + hex(SHA-256(body))

Simulation hooks

A backend with a simulated device can offer these, so api-check --sim and your own tests can make “an SMS arrives” and “a call rings” happen. They are outside /v1, take no token, and are open only to the backend's own machine (loopback). They are a convention for tests, not part of the API: the app never calls them, and a backend driving a real device must not offer them.

HookBodyWhat happens
POST /_sim/sms{ "from", "text" }An SMS arrives.
POST /_sim/call{ "from" } (null: withheld)A call rings.
POST /_sim/hangup{}The far end hangs up; a call still ringing is then missed.
POST /_sim/answer{}The far end answers the outgoing call. Optional: a simulator may answer by itself.

Each answers 200 {}, or 409 when it does not fit (a call already up, say).

test-relay.mjs: relay stand-in

Tests your pushes without the real relay or Apple. It checks what the relay checks (the enrolment proof, every signature, the clock, nonces, that pushes are sealed) and opens each sealed payload with the client tokens it is given, so you see what the phone would get. When something the relay would pass but the app relies on is wrong (category, collapse id, sound, interruption level, the sealed fields), that log line carries warnings. It prints one JSON line per request on standard output.

Point your backend's relay address at it (an override for tests: POST /v1/push/enrol itself takes https only), then enrol from the app or directly with POST /v1/push/enrol; any 16–200 characters will do as a grant. The grant expired-grant-for-testing is always refused, like an expired one. --state <file> keeps the enrolled backends in a file, so the stand-in does not need a new enrolment after a restart.

FAQ

My backend is not on the LAN. How does the app reach it?

Give a remote path in the endpoint list; see Endpoints and remote access. The app uses the best one by priority that connects, and moves up when a better one gets through.

Do I have to implement snapshot?

No. Without it the app reads each list at every connection, and the result is just as correct. With it, the app sends no request when nothing changed, which suits mobile networks.

Can I get pushes without an Apple developer account?

Yes. Pushes go through the CellPilot relay, so you need no Apple developer account. Implement the push feature; once the user signs in with Apple in the app, the app enrols you on the relay.

The phone did not ring for a call?

A call needs a VoIP push to bring up the system call screen. Check that you received a token with kind: "voip", that type is "voip" when you push through the relay, that the push body has only e and v, and that the sealed content has callId and number (see Push payloads). Expiry, topic and the like are set by the relay; you need not handle them. When the user turns the system call screen off, the app withdraws its VoIP token, and calls then go out as ordinary call alerts. test-relay.mjs opens sealed payloads, so you can see what the phone would get.
